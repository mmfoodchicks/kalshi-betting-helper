## 1. Verdict

**AGREE AFTER FIXES.** The design is sound and carefully hedged. The compound engine is right: it matches my own
brute-force simulation. The licence default is enforced. The feature lists are generated from code and pinned to the
rule text. But the rule cannot be hashed as it stands, for one reason that is a blocker and several that are
cheap to fix now and impossible to fix after the hash:

- **The machinery the rule describes does not exist yet** (B1). The gate, the walk, the 2026 check, the prospective
  step and the export are prose only. The code that would be registered cannot read 2025 outcomes at all.
- **Three fitted features are all zeros**, and one of them flips between the two frames (M1). A null CFP result would
  not be a finding about run direction.
- **Six specification holes** (M2, M3) mean two honest implementers would fit different models.
- The prospective reader cannot read weeks 8-11 as registered (M5), and the inactive-player treatment does not match
  the board (M4).

Required changes are listed in section 4. None needs a design change; all are text or code to add before the hash.

## 3. Findings

### BLOCKER

**B1. The machinery the rule describes does not exist, so the hash would bind a rule no code runs.**
- Evidence:
  - `research/nfl_rush_model_fit.py` has `traincheck`, `traincheck_frame`, `audit` and `register`, and nothing else
    (`main` choices, line 734). There is no ladder, no ridge quasi-Poisson fit, no gate (`accept`), no 2025 walk, no 2026
    check, no prospective step, no export, no `prospective_lock.json`. The file says so ("the ladder and the validate /
    test commands join when the rushing data layer is agreed").
  - Q9 registers the bytes of `research/nfl_rush_model_fit.py`. Code added after the hash is not the registered
    code; code added before it has not been reviewed.
  - `FORBIDDEN = (2025, 2026)` / `_guard` is unconditional, tied to no registration. The registered file therefore
    cannot read a 2025 outcome. Either the file changes after the hash, or the scoring code lives outside the
    registered set.
  - Q9's last line, "Every command refuses when a file or this block no longer hashes to what was registered",
    has no implementing command.
  - The first model's precedent had `validate`, `test`, `export` and `check_prereg` all written, reviewed and hashed
    before scoring. Its review still found F1 (the yards-family choice compared NaN with NaN, so the first family won
    by loop order) in that code after the fact. Here nothing can be checked in advance.
- Consequence: gate, SE use, walk, window, refusals and export cannot be mutation-tested (they are absent from
  section 5), and the rule's decidability (M2) cannot be demonstrated by running it.
- Fix: write the ladder, `validate`, `test` (with the 2026 secondary and `test_lock`), the prospective command with
  `prospective_lock.json`, and `export`, before the hash. Include them in `REG_CODE`. Make the outcome hold lift only
  when `prereg.json` exists and its rule block, code and data hashes all match (the first model's `check_prereg`).
  Have the Sonnet and Opus reviewers and the orchestrator review that code against the rule text, with my mutation
  targets (gate, SE, walk, window, refusals, export) as required guards. Replay the gate and the walk on the committed
  JSONs in a guard, so `shipped` can only equal what the rule produces (the first model's F7).

### MAJOR

**M1. Three fitted features are identically zero and one flips between frames; the rule does not say so.**
- `cfp_direction` (RB CFP) is exactly 0.0 on every RB row of both frames (1,801 rows in 2025 alone) and every season.
  `cfp_dsg_edge` (QB CFP) is exactly 0.0 or blank on every row. `spd_qb_td_oe` (QB TD, the only term in that SPD
  group) is exactly 0.0 on every row of the test frame, but alive in the validation frame (SD 0.029 / 0.033 / 0.034 in
  2023 / 2024 / 2025).
- Cause: the data layer measured the defense-side signals `def_side_ypc_dev`, `def_dir_ypc_dev` and (pooled)
  `def_rush_tds_oe` as unsupported (`reliability.json` `unsupported` / `k` None), so their deviations shrink to the
  prior. Nine metrics change supported-status between `k_fit_only` and the pooled `k` (e.g. `def_rush_tds_oe`: k 63.6
  fit-only, None pooled).
- In 2023, five of the six QB CFP features (all but `cfp_scr_blitz`) and `full_scr_x_margin` are zero on every row
  (participation charts scrambles only from 2023, and the mask leaves 2021-22; plus `cfp_dsg_edge`), so the
  leave-one-season-out CV for that group has one fold in which almost no column carries information.
- Consequences:
  1. The owner's "run direction / gap weaknesses" request is untested, and the report's section 4 ("every feature
     not listed has zero missing") reads as if it were.
  2. QB TD SPD can pass 2025 on the fit-only support, then in the test / production frame be a column of zeros. The 2026
     check reads `d = 0 <= 0` and keeps it as PROVISIONAL (a board label on a term that does nothing); the prospective
     `d < 0` finally reverts it.
  3. "Columns over their training SD" divides by zero for these columns; the rule does not say what happens.
  4. `paths_absent` / Q9's "never fitted on a column of zeros" test key presence, not variance.
- Fix: say it in Q3a and section 4 (list the dead features and why); drop zero-SD columns by rule; build both frames on
  ONE supported set or state that a group whose live terms are all dead in the test frame cannot be kept (a tie
  `d == 0` must not pass `d <= 0`); make registration refuse a fitted feature with zero variance in the training seasons
  of a frame unless the rule names it; recount the decisions (QB TD SPD cannot be accepted in the test frame).

- **Fit universe, response, SD.** The rule gives scoring universes (Q1) but not the rows each GLM is fitted on, the

- **The yards offset chain.** Q3b: yards per attempt is fitted "with offset log(Sleeper's yards) + the count's accepted

- **Derived-market baselines.** RB and QB anytime TD "use their components' accepted models" (Q3), but which factor

- **QB terms to components.** Q2: "QB designed runs, scramble rate, or yards per designed run / per scramble". Q3a labels

**M4. Inactive players are scored 0, but the board's probability is conditional on playing.**
- Q1: "A frozen-projected player with no box line did not play and scores 0." Kalshi settles an inactive player at the
  last fair price, and the board prices "conditional on his entering" (`CLAUDE.md`). The test therefore rewards or
  punishes terms for what they do on a population the board never claims to price.
- The asymmetry: on the revised lines of 2023-24 only 1 / 2 of ~840 RB rows (0.1-0.2%) are inactive (the revised line
  already dropped them), but the 2026 frozen universe keeps them; 8 of 182 frozen RB rows were "questionable" on the
  pre-game report (4%).
- Sizing: a row that scores 0 against a 14-carry projection carries 2-4 nats; a candidate that moves its mean 5% changes
  that row by ~0.2-0.5 nats. Two or three such rows in ~200 prospective RB rows add 0.003-0.005 to d, the size of the 0.004
  floor and larger than a typical mean-term gain (0.002). They can decide a coin-flip KEEP.
- Fix: decide on rows where the player played (report the number dropped), report the all-rows figure beside it; or
  state why the all-rows figure is the right one for a board that claims conditional probabilities.

**M7. Nothing in code stops a failed group reaching the board.**

**M8. The error control is weaker than the text says, and the label overclaims.**

- Fix: state these numbers in Q3b; report a player-clustered SE beside the game-clustered one and gate on the larger; have
  the board say "kept on a point estimate (d = x, n games)" rather than "shipped"; state that DEC's 2025 pass is no
